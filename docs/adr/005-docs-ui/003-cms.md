# 005-003. Data-Driven ADR & Tooling Maturity CMS

Date: 2026-11-21
Status: Proposed (for owner review before DB & UI implementation)
Parent: [005-docs-ui](../005-docs-ui.md)

## Context

ExoNovel will remain in active development while foundational technologies (e.g., `willow25`, `iroh`, Rust CRDT engines, `leptos`, global payment connectors) mature toward production stability. Planned ExoNovel features that depend on unreleased or stabilizing capabilities of underlying libraries are **on hold** until those capabilities ship.

Relying solely on static `.md` files on disk makes it difficult to query which product requirements are blocked, which tool version unlocks them, or to record release-triggered upgrade proposals directly inside the app. Therefore, ExoNovel's built-in documentation reader is overhauled into a **data-driven ADR & Tooling Maturity Content Management System (CMS)** backed by **Neon PostgreSQL**.

## Decision

### 1. Database as the Primary Source of Truth (Startup Seed/Sync)
- Replace static file reads in the Docs Reader with structured **Neon PostgreSQL** tables so ExoNovel owns and hosts its own maturity management workflow directly inside `https://exonovel.exosystems.net`.
- On server startup, bootstrap/sync any unimported files from `docs/` into the relational tables cleanly so zero historical decisions are lost during transition, after which edits, new ADRs, tooling rows, and release notes are managed in Neon PostgreSQL (and optionally exportable back to Markdown/Willow coordinates).

### 2. Full MADR 4.0.0 + Maturity Relational Data Model
Grounded in **MADR v4.0.0** (Markdown Architectural Decision Records) and ExoNovel's Willow portability rules (`willow_namespace`, `willow_subspace`, `willow_path`, `willow_timestamp_us`):

- **`adr_records`**:
  - `id`, `adr_number` (e.g., `003`, `003-002`), `parent_adr_id` (self-FK for hierarchical ADRs/sub-ADRs), `doc_kind` (`adr`, `report`, `scope`, `guide`)
  - `title`, `slug`, `status` (`proposed`, `accepted`, `on-hold`, `ready-to-build`, `rejected`, `deprecated`, `superseded`)
  - `superseded_by_id`
  - **MADR Core Sections**: `context_problem`, `decision_drivers`, `considered_options_json`, `decision_outcome`, `consequences_pros_cons`, `confirmation_criteria`
  - **RACI / Governance**: `decision_makers`, `consulted`, `informed`, `author_did`, `willow_*` coordinates, `created_at`, `updated_at`
- **`tooling_catalog`**:
  - `tool_id`, `name` (e.g., `willow25`, `loro`, `iroh`, `leptos`, `airwallex`), `ecosystem` (`cargo`, `saas`, `protocol`, `sdk`), `category` (`crdt`, `p2p-sync`, `auth`, `payments`, `i18n`, `push`, `web-ui`), `repo_or_registry_url`, `license`, `maturity_tier` (`experimental`, `beta`, `production`), `description`
- **`tooling_versions`**:
  - `version_id`, `tool_id` (FK -> `tooling_catalog`), `version_semver`, `is_installed_in_exo`, `is_latest_upstream`, `release_date`, `changelog_url`, `capabilities_unlocked`, `breaking_changes`
- **`adr_tooling_dependencies`** (Linking Requirements to Tooling Versions):
  - `id`, `adr_id` (FK -> `adr_records`), `tool_id` (FK -> `tooling_catalog`), `required_version_id` (FK -> `tooling_versions`), `dependency_kind` (`blocking`, `recommended`, `evaluating`), `requirement_note`, `satisfied` (boolean)
  - Whenever an ADR states a requirement that cannot ship yet (for example, live Google Docs-style simultaneous editing in `003-content` awaiting a chosen CRDT version), its `status` is **`on-hold`** and its foreign keys point to the `tooling_versions` row required to unblock it.
- **`adr_translations`** (Synchronized Multilingual Editions per `AGENTS.md` Rule 18):
  - `id`, `adr_id` (FK -> `adr_records`), `locale` (`de`, `pl`, ...), `UNIQUE(adr_id, locale)`
  - Stores localized `title`, `context_problem`, `decision_drivers`, `decision_outcome`, `consequences_pros_cons`, `confirmation_criteria`, and `raw_markdown`, plus timestamps so non-English edits never overwrite canonical English rows and missing locales fall back cleanly to English.
- **`maturity_proposal_notes`** (Living Release Proposals):
  - `note_id`, `tool_id`, `version_id`, `adr_id` (nullable if proposing a brand-new capability), `proposed_by` (`owner` / `agent-watch`), `proposal_title`, `new_capability_summary`, `how_exonovel_benefits`, `review_status` (`open`, `accepted`, `dismissed`), `created_at`
  - When a watched dependency releases a new version (surfaced by ExoNovel's deterministic `crates.io` / GitHub release scanner, while `dependabot.yml` separately handles safe weekly hygiene updates for installed dependencies), a maturity note is logged explaining **new features/abilities unlocked that we could not previously plan for**, with a **Draft ADR from Proposal** action to promote an open proposal directly into the structured MADR editor.

### 3. In-App CMS Interface (Replaces Read-Only Docs Viewer)
- **Tree & Maturity Filter Sidebar**: Browse ADRs by parent/sub-ADR hierarchy, filter by status (`on-hold`, `ready-to-build`, `accepted`, `proposed`) or doc kind (`adr`, `report`, `scope`), and auto-collapse after mobile document selection.
- **Structured MADR Form Editor** (admin-gated): Create or edit any ADR, report, or guide using guided fields (Status, Decision Drivers, Options with Pros/Cons, Decision Outcome, Tooling Dependencies picker linking directly to `tooling_versions`), localized to the active UI language (`en`, `de`, `pl`).
- **Tooling & Proposals View** (separated cleanly from inference runtime config): Manage watched dependencies, trigger deterministic `crates.io` / GitHub scans, inspect unlocked versions, and generate or promote **Maturity Proposals** (`Draft ADR from Proposal`).
- **AI Inference View**: Separate admin view managing configured headless CLI and API inference runtimes (`OpenCode` CLI + keyed providers such as `NVIDIA NIM`), active current-generation free models, and catalog refresh.
- **Owner-Editable Feedback Loop**: Owner edits saved in the CMS DB become authoritative context for future agent work.

### 4. Automated Maturity Scanner Architecture (`.github/dependabot.yml` + Ecosystem Poller)
ExoNovel strictly separates **installed dependency hygiene** from **roadmap / `on-hold` capability intelligence**:
1. **GitHub Dependabot (`.github/dependabot.yml`) — Installed Manifest Hygiene Only**:
   - **Scope Reality (2026-11-22 Architectural Correction)**: Dependabot can only read crates already declared in `Cargo.toml` / `Cargo.lock` and actions declared in `.github/workflows/*.yml`. An earlier `2026-11-21` draft incorrectly set `cargo` checks to `daily` with ungrouped limits (`open-pull-requests-limit: 10`) to "watch" uninstalled `on-hold` crates (`willow25`, `iroh`, `loro`, `leptos-fluent`, `web-push`). That misdesign immediately flooded the repository with 10 uncompilable breaking major-version Rust PRs plus 5 CI Action PRs on a single push.
   - **Corrected Standard Design**:
     - **Cargo (`weekly`, Monday `06:00` UTC, `versioning-strategy: "lockfile-only"`)**: Uses grouped lockfile-only version updates (`cargo-compatible`), supply-chain cooldowns (`default-days: 7`, `semver-minor-days: 7`, `semver-patch-days: 3`), and never edits `Cargo.toml` for breaking bumps — closing Dependabot's `ignore: semver-major` blind spot on pre-1.0 `0.x -> 0.y` releases (`comrak 0.35 -> 0.59`, `gloo-net 0.6 -> 0.7`) as well as `N.x -> N+1.0` majors (`sqlx 0.9`, `ed25519-dalek 3`), which are planned deliberately in [006-001](../../006-stack/001-releases.md).
     - **GitHub Actions (`weekly`, Monday `06:00` UTC)**: Groups all workflow runner updates into one weekly PR (`github-actions-all`) with a 7-day cooldown, paired with Node-24-compatible action majors and PR concurrency cancellation in `.github/workflows/deploy.yml`.
2. **In-App Maturity Scanner: Deterministic Code Core vs. Optional AI Composition**:
   - **100% Deterministic Rust Code (Zero AI Required)**:
     - Polls `crates.io` JSON API, GitHub Releases, and tagged Milestones/Issues/Discussions on watched repositories (`willow25`, `iroh`, `loro`, `leptos`, `leptos-fluent`, `web-push`, `sqlx`).
     - Matches exact crate names and declared `required_version` semver constraints in `adr_tooling_dependencies` (plus explicit keyword/label tags on ADR rows) to automatically mark satisfied `on-hold` ADRs as **`ready-to-build`**, store release changelogs in `tooling_versions`, and open draft `maturity_proposal_notes` records for review.
   - **Optional AI Proposal Synthesis (AOTA Pluggable Headless CLI Runner)**:
     - Reading unstructured release prose, blog posts, or roadmap discussions to *invent creative prose proposals* for unanticipated ExoNovel capabilities requires natural-language reasoning.
     - ExoNovel invokes **`OpenCode`** (`opencode run --standalone --auto --format json`) with direct fallback to actively keyed free providers (**NVIDIA NIM**, plus additional providers strictly once their API keys are configured; see [004-inference](004-inference.md)).
   - Dispatches an Admin notification (in-app + push + Brevo email via `notes@exosystems.net` / `"Notes from ExoNovel"`, see [008-notify](../../008-notify.md)).
